# ADR-0002: PostgreSQL-backed worker вместо отдельного брокера

- Статус: Accepted
- Дата: 2026-11-20

## Контекст

После согласования операция должна выполняться фоном, переживать остановку приложения и допускать настраиваемую паузу после неопределённого ответа. Задание явно разрешает запуск фонового обработчика вместе с приложением и не требует собственный брокер.

Брокер сам по себе не устраняет неопределённость provider call. Наивное использование брокера также создаёт dual write между PostgreSQL и queue.

## Решение

Использовать таблицу `renewal_jobs` в PostgreSQL и stateless polling worker:

- job создаётся в одной транзакции с approve;
- `request_id` уникален;
- выполнение планируется через `next_attempt_at`;
- владение задачей защищается lease и row locks/`SKIP LOCKED`;
- каждый claim увеличивает `execution_version`; scheduling/attention/finalize принимаются только от текущей версии, поэтому поздний результат прежнего владельца отбрасывается;
- следующее действие (`POST`/`RECONCILE`) и counters хранятся в БД;
- просроченный lease восстанавливается через reconciliation;
- worker запускается вместе с приложением в MVP, но физически может быть вынесен в отдельный процесс без смены модели данных.

Гарантия — at-least-once processing. Exactly-once внешнего эффекта обеспечивается только идемпотентностью провайдера; DB finalization идемпотентна.

При фатальном отказе in-process worker процесс должен завершиться либо supervisor должен перезапустить worker. Живой API с незаметно остановленным worker не считается корректным состоянием.

## Последствия

### Положительные

- Нет dual write с внешней очередью.
- Нет отдельной инфраструктуры и дополнительных секретов.
- Recovery и контрольный сценарий воспроизводятся только с PostgreSQL и приложением.
- Состояние задач можно проверять SQL и integration tests.

### Отрицательные

- Polling не подходит для высокой нагрузки.
- Нет готовых broker UI, DLQ и sophisticated routing.
- При незапущенном приложении нет выполнения, хотя задачи сохраняются.
- PostgreSQL требует аккуратного claim/lease протокола.

## Альтернативы

- **In-memory queue/setInterval:** отклонено, задачи теряются при перезапуске.
- **RabbitMQ/Kafka/Redis queue:** избыточно для MVP и не отменяет необходимость idempotency/recovery.
- **Синхронный provider call во время approve:** отклонено, усложняет восстановление и удерживает бизнес-запрос на время внешнего вызова.

## Будущая миграция к брокеру

При росте нагрузки добавить transactional outbox и publisher. Просто отправлять broker message после commit без outbox нельзя: падение между commit и publish потеряет задачу.
