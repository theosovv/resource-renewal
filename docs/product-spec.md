# Product Specification — Resource Renewal

## 1. Цель

Разработать самостоятельное приложение, в котором инициатор создаёт заявку на продление ресурса, другой сотрудник согласовывает или отклоняет её, а приложение выполняет операцию через тестовый provider API.

Система MUST корректно обрабатывать неопределённый ответ провайдера и MUST NOT создавать вторую внешнюю операцию или повторно изменять срок ресурса.

## 2. Границы MVP

### Входит

- локальный вход для заранее созданных пользователей;
- пространства Alpha и Beta с изоляцией данных;
- список ресурсов и заявок;
- создание, согласование и отклонение заявки;
- история переходов;
- persistent background worker;
- интеграция с имитатором провайдера;
- ручной повтор из состояния «Требует внимания»;
- миграции, seed-данные, OpenAPI, тесты и инструкции запуска.

### Не входит

- регистрация, SSO, восстановление пароля;
- CRUD пользователей, пространств и ресурсов;
- уведомления;
- production deployment и HA-инфраструктура;
- отдельный брокер сообщений;
- произвольные периоды продления и валюты;
- гарантия exactly-once для внешнего API без идемпотентности;
- обработка перезапуска имитатора во время незавершённой операции.

Дополнительный функционал MUST NOT разрабатываться в ущерб обязательному сценарию.

## 3. Пользователи и доступ

### 3.1 Роли

| Роль | Разрешения |
|---|---|
| `INITIATOR` | Просматривать ресурсы и заявки своего пространства, создавать заявки |
| `APPROVER` | Просматривать ресурсы и заявки своего пространства, согласовывать, отклонять и повторять обработку |

Просмотр разрешён любому пользователю, имеющему membership в пространстве. Универсальный пользователь имеет обе роли, но не может принимать решение по собственной заявке.

### 3.2 Seed-аккаунты

| Логин | Пространство | Роли |
|---|---|---|
| `initiator.alpha@example.test` | Alpha | `INITIATOR` |
| `approver.alpha@example.test` | Alpha | `APPROVER` |
| `initiator.beta@example.test` | Beta | `INITIATOR` |
| `universal.alpha@example.test` | Alpha | `INITIATOR`, `APPROVER` |

Пароли MUST быть вымышленными, храниться только в виде Argon2id-хешей и быть описаны в итоговом README для локальной проверки. Вход MUST принимать только логин и пароль; пространство и роли нельзя назначать через запрос.

### 3.3 Начальные данные

| Пространство | Внешний ID | Название | Срок | Стоимость |
|---|---|---|---|---|
| Alpha | `res-a-01` | Хранилище A | `2027-03-01` | 128000 копеек, RUB |
| Alpha | `res-a-02` | Сервис B | `2027-05-20` | 250000 копеек, RUB |
| Beta | `res-b-01` | Сервис C | `2027-06-01` | 150000 копеек, RUB |

Seed MUST быть повторяемым и MUST NOT дублировать данные при повторном запуске. Повторный seed после появления бизнес-операций MUST NOT перезаписывать текущие сроки и заявки; для повторной приёмки используется отдельная команда чистого сброса, явно помеченная как опасная.

## 4. Модель состояния

| Статус API | Отображение | Активная | Допустимые действия |
|---|---|---:|---|
| `PENDING_APPROVAL` | На согласовании | Да | Согласовать или отклонить другим approver |
| `REJECTED` | Отклонена | Нет | Только просмотр |
| `PROCESSING` | Выполняется | Да | Ожидание worker |
| `COMPLETED` | Завершена | Нет | Просмотр; создание новой заявки на ресурс |
| `NEEDS_ATTENTION` | Требует внимания | Да | Просмотр и ручной retry approver |

Переходы:

```text
CREATE → PENDING_APPROVAL
PENDING_APPROVAL → PROCESSING       (approve)
PENDING_APPROVAL → REJECTED         (reject)
PROCESSING → COMPLETED              (provider confirmed)
PROCESSING → NEEDS_ATTENTION        (uncertain/non-retryable failure)
NEEDS_ATTENTION → PROCESSING        (manual retry)
```

Все прочие переходы запрещены и возвращают `409 INVALID_STATE_TRANSITION`. Системные переходы выполняет worker; клиент не может напрямую установить статус.

## 5. Функциональные требования

### Данные и доступ

- **FR-DATA-001.** Приложение MUST создать два пространства, четыре учётные записи и три ресурса из раздела 3.
- **FR-DATA-002.** Стоимость MUST храниться целым числом копеек, валюта — `RUB`, срок — календарной датой без времени.
- **FR-DATA-003.** Для ресурса MUST быть доступны текущий срок и история его заявок.
- **FR-AUTH-001.** Вход MUST быть локальным; регистрация и refresh-token flow не реализуются. После успешного login создаётся новая server-side session.
- **FR-AUTH-002.** Сервер MUST определять пользователя по opaque session cookie и записи `auth_sessions`, а права — по актуальным membership в БД. Роль, пространство и user ID MUST NOT приниматься как авторитетные поля запроса или cookie.
- **FR-AUTH-003.** Без действующей сессии API MUST возвращать `401`; при отсутствии доступа к пространству или действию — `403`.
- **FR-AUTH-004.** Session cookie MUST быть `HttpOnly`, `SameSite=Lax`, `Path=/` и `Secure` вне явно настроенного local HTTP. В БД сохраняется только SHA-256 hash случайного session token; raw token не попадает в Web Storage/response body. Действуют idle expiry 30 минут и absolute expiry 8 часов; logout отзывает текущую сессию.
- **FR-AUTH-005.** Все authenticated unsafe methods MUST требовать session-bound `X-CSRF-Token`; отсутствующий/неверный token возвращает `403 CSRF_INVALID`. CORS credentials разрешены только для configured web origin; Origin/Fetch Metadata проверяются как дополнительный уровень. SPA получает CSRF token из login response или `GET /auth/csrf` и хранит его только в памяти.
- **FR-TENANT-001.** Каждый запрос ресурса/заявки MUST проверяться в контексте пространства. Пользователь одного пространства MUST NOT читать или изменять данные другого, в том числе по известному UUID.

### Заявки

- **FR-REQ-001.** Инициатор создаёт заявку, указывая только ресурс внутри выбранного пространства. Сервер сам рассчитывает продление на 30 календарных дней от текущего срока.
- **FR-REQ-002.** При создании MUST фиксироваться сумма, валюта, прежний и новый сроки. Последующее выполнение использует только этот снимок.
- **FR-REQ-003.** У ресурса может быть не больше одной активной заявки. Ограничение MUST быть закреплено частичным уникальным индексом PostgreSQL и работать при параллельных запросах.
- **FR-STATE-001.** Согласование и отклонение доступны только из `PENDING_APPROVAL`; повтор и недопустимый переход возвращают `409`.
- **FR-STATE-002.** Пользователь MUST NOT согласовывать или отклонять собственную заявку. Нарушение возвращает `403 SELF_DECISION_FORBIDDEN`.
- **FR-STATE-003.** При согласовании сервер MUST сверить текущие срок, стоимость и валюту ресурса со снимком. При расхождении — `409 RESOURCE_SNAPSHOT_MISMATCH`, без создания job и обращения к провайдеру.
- **FR-STATE-004.** Отклонённая заявка MUST завершаться без provider call и изменения ресурса.
- **FR-HIST-001.** История MUST содержать автора или системный actor, timestamp, прежний и новый статусы. Секреты, password hash, raw session/CSRF tokens и полный ответ провайдера сохранять запрещено.

### Интеграция и надёжность

- **FR-INT-001.** Для каждой заявки создаётся стабильный `operation_key`. Все POST и GET используют его; URL path parameter MUST быть percent-encoded.
- **FR-INT-002.** POST содержит внешний `resource_id`, `period_months: 1`, сумму и валюту из неизменяемого снимка.
- **FR-INT-003.** После `503` результат считается неизвестным. Разрешены только GET по ключу или POST с тем же ключом и телом. Нормализация суммы/даты из текущего ресурса при retry запрещена.
- **FR-REL-001.** Согласование, создание persistent job и история MUST фиксироваться атомарно.
- **FR-REL-002.** Подтверждение провайдера, результат операции, статус заявки, завершение job, история и новый срок ресурса MUST обновляться в одной транзакции.
- **FR-REL-003.** Повторная финализация MUST быть no-op и MUST NOT снова изменять срок.
- **FR-REL-004.** Если результат не определён после трёх POST-attempt, заявка переходит в `NEEDS_ATTENTION`. GET не считается POST-attempt.
- **FR-REL-005.** Approver MAY вручную повторить обработку из `NEEDS_ATTENTION`. Используется прежний ключ, заявка остаётся активной, новая заявка на ресурс недоступна.
- **FR-REL-006.** Задержка после неопределённого POST MUST настраиваться и сохраняться как `next_attempt_at`. После перезапуска приложения worker MUST продолжить обработку, не полагаясь на память прежнего процесса.
- **FR-REL-007.** Параллельные согласования MUST дать не более одного успешного перехода и одну job; последующие запросы получают `409`.

### Интерфейс

- **FR-UI-001.** UI MUST предоставить вход, выбор доступного пространства, список ресурсов/заявок, создание заявки, детали с историей и действия approver.
- **FR-UI-002.** UI MUST отображать статус, текущий срок, стоимость, ошибки, загрузку и пустое состояние. Операция и provider operation ID показываются в деталях для проверки, если уже существуют.
- **FR-UI-003.** Desktop-страница SHOULD визуально соответствовать референсу: фон `#0B1B1D`, карточка `#1D2C2E`, текст `#F5F7F7`, вторичный текст `#A9B8B9`, акцент `#80A3FF`, Arial, заголовок 32 px, основной текст 14–16 px, радиус 20 px, отступ 24 px.
- **FR-UI-004.** При viewport 390 px MUST NOT быть наложений и горизонтального скролла страницы; таблица MAY заменяться карточками. Desktop проверяется на 1440×900, контент — `min(1120px, 100% - 64px)`.
- **FR-UI-005.** Основные действия MUST работать с клавиатуры; интерактивные элементы имеют видимый focus, формы — связанные labels, динамические ошибки — доступное текстовое представление.

### Проверка и сдача

- **FR-TEST-001.** Автоматические тесты MUST проверять бизнес-переходы, права, изоляцию, повторное/параллельное согласование, recovery и однократное изменение срока через API и реальную БД.
- **FR-DOC-001.** README MUST содержать точные версии, команды запуска БД/API/web/worker/имитатора, миграции, seed, тесты, учётные записи, задержку retry, operation key для проверки и ограничения.
- **FR-DOC-002.** README MUST описывать state machine, обработку неопределённости, защиту от дублей, компромиссы и незавершённые пункты.

## 6. Правила HTTP-ошибок

| Ситуация | Ответ |
|---|---|
| Нет/недействительна/expired/revoked session cookie | `401 UNAUTHORIZED` |
| Нет/неверен CSRF token для unsafe method | `403 CSRF_INVALID` |
| Нет membership в пространстве из path | `403 FORBIDDEN` |
| Нет нужной роли | `403 FORBIDDEN` |
| Собственное решение по заявке | `403 SELF_DECISION_FORBIDDEN` |
| Ресурс/заявка не найдены внутри доступного пространства | `404 RESOURCE_NOT_FOUND` / `REQUEST_NOT_FOUND` |
| Уже есть активная заявка | `409 REQUEST_ALREADY_ACTIVE` |
| Недопустимый или повторный переход | `409 INVALID_STATE_TRANSITION` |
| Снимок не совпадает с ресурсом | `409 RESOURCE_SNAPSHOT_MISMATCH` |
| Некорректное тело/параметр | `400 VALIDATION_ERROR` |

Для чужого пространства сначала проверяется membership, поэтому возвращается `403` независимо от существования внутреннего UUID. Внутри доступного пространства чужой или несуществующий объект не раскрывается и возвращает `404`.

## 7. Acceptance Criteria

- **AC-01.** Создание заявки на `res-a-01` фиксирует `2027-03-01 → 2027-03-31`, 128000 RUB; срок ресурса до подтверждения не меняется.
- **AC-02.** Вторая последовательная или параллельная активная заявка на тот же ресурс отклоняется с `409`; в БД остаётся одна активная запись.
- **AC-03.** Beta initiator получает `403` при чтении/изменении Alpha по известному ID; unauthenticated запрос получает `401`.
- **AC-04.** Universal Alpha может создать заявку, но получает `403` при попытке одобрить или отклонить её сам.
- **AC-05.** Два параллельных одобрения дают один успешный ответ и один `409`, одну job и один переход согласования в истории.
- **AC-06.** После первого `503` приложение можно остановить до следующего provider call. После запуска оно использует прежний ключ и завершает заявку.
- **AC-07.** После завершения срок равен `2027-03-31`; повторная обработка его не меняет. `GET /renewals/{key}` возвращает `started_count=1`, stats ресурса — `operation_count=1`.
- **AC-08.** Отклонённая заявка не вызывает провайдера и не меняет срок; stats другого ресурса остаётся `0`.
- **AC-09.** Три неопределённых POST приводят к `NEEDS_ATTENTION`; GET не увеличивает счётчик; manual retry использует тот же ключ.
- **AC-10.** Ошибки, статусы и переходы видны в UI и истории; основной сценарий доступен с клавиатуры и на mobile без горизонтального скролла.

## 8. Принятые допущения

1. Manual retry — повтор технической обработки уже согласованной заявки, а не новое бизнес-решение. Доступен любому approver пространства, включая universal; собственное первичное согласование по-прежнему запрещено.
2. При ручном retry сначала выполняется reconciliation GET. Счётчик автоматических попыток нового цикла сбрасывается, общий счётчик сохраняется для наблюдаемости.
3. Неповторяемая ошибка провайдера, например idempotency payload conflict, MAY перевести заявку в `NEEDS_ATTENTION` раньше трёх POST. Три попытки относятся к неопределённым/временным ошибкам.
4. При stale snapshot заявка остаётся `PENDING_APPROVAL` и может быть отклонена другим approver. Автоматическая отмена не выполняется.
5. В MVP нет pagination: предполагается маленький тестовый набор. API не обещает production-лимиты.
6. Имитатор остаётся запущенным на протяжении recovery-сценария. Его in-memory состояние не является ответственностью приложения.
